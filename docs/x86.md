# 32-bit (x86) files

`exediff.exe` is one program for both architectures. It reads the PE header of each input and takes the PE32 or PE32+ path by itself, so it also compares 32-bit exes and DLLs. The two files must have the same architecture; a mixed pair stops with `old is x64 but new is x86: both files must have the same architecture` and exit code 1.

What differs from x64:

| | x64 | x86 |
|---|---|---|
| Where functions come from | `.pdata` (exact start and end of every function, plus chunks) | Not stored in the file. Found by the rules below. |
| Absolute addresses in code | RIP-relative displacements | Absolute disp32/imm32 operands, listed in `.reloc` (type 3, HIGHLOW) |
| Import thunks | 8 bytes | 4 bytes |
| Chunks (split functions) | yes | none: an x86 function is one range |

## How x86 functions are found

`src/func/seeds.cpp` and `x86_protos` in `src/func/discover.cpp`.

1. **Seeds.** The entry point and the named exports. 4-byte relocated pointers stored outside code that point into code (vtables, callback tables) are weaker seeds: they are used last, and dropped when they fall inside a function already found (a switch table in `.rdata` is made of such pointers).
2. **Call targets.** Every `call` inside a function found so far is a new start.
3. **Padding.** The code after a run of `int3`/`nop` that follows a function's end is a new start.
4. **The end of a function** (`padded_end`): decode forward; the farthest forward branch (and the entries of an indexed `jmp [index*4+table]`) keep the function open; it ends after the `ret` or `jmp` that nothing branches beyond, or at an `int3`:
   - that follows noreturn code and is not covered by a branch, or
   - that comes straight after a `ret` or `jmp`. That is padding, and an earlier branch past it is a tail jump to another function, not part of this one.
   If the first instruction does not decode, or the code runs into the end of its section, the start is **skipped** and listed (see below).

The result is sorted and disjoint. Everything after discovery (masking, hashing, matching, rendering) is shared with x64.

## Masking

- A relocated disp32 or imm32 is replaced by what it points at (an import, a string, a function, or the section), so a function that only moved, or whose globals moved, is not reported as changed.
- A relative `call`/`jmp` target is an rva already, not an absolute address; it is named by the matched function.
- **Without relocations** (`/FIXED`, the `RELOCS_STRIPPED` flag, or an empty `.reloc`): there is no list to tell an address from a number, so any 32-bit operand that lies inside the image's range is masked. The report says so (`no relocations in <file>: absolute addresses masked by range`). The risk is a constant that happens to fall inside the image range (for example `0x401000` used as a plain number): it is masked, so a change of that constant alone is not seen.

## Notes in the report

`report.html`, `agent.md` and the full Markdown start with the architecture and, for x86, one note per file:

- `N functions found, B of E code bytes outside any function`: `E` is the size of the executable sections without runs of `int3`/`nop` padding, `B` is how much of that no function covers. "Outside" means jump tables and other data inside `.text`, and code that no seed, call or padding rule reaches (for example reached only through a computed jump). It is not an error count; a comparison never sees changes inside it.
- `K function starts skipped: <reason> (first 0x..., ...)`: a start that was found and could not be used (`start does not decode`, `no end inside the section`).
- the no-relocations note above.

## Measurements

`Trove_x86.old.exe` / `Trove_x86.new.exe` (PE32, base `0x400000`, `.text` about 13 MB, relocations present, 276 named exports):

| | old | new |
|---|---|---|
| functions | 63,516 | 63,456 |
| skipped starts | 0 | 0 |
| code bytes outside any function | 464,954 of 13,031,450 (3.6%) | 473,500 of 13,030,325 (3.6%) |
| discovery time | 1.1 to 1.3 s | 1.1 to 1.3 s |

Comparison without IDA: 241 changed, 773 calls changed, 63 added, 123 removed, 62,379 identical. Of the 62,379 identical pairs, 355 are rendered with a different callee name only and 316 are tiny getters that reference another global (the matcher treats functions with equal hashes as interchangeable); none of the longer ones renders differently.

x64 results are unchanged by the x86 work (`Trove_x64` pair: 35 changed, 2 added, 1 removed, 55,497 identical; `map.csv` identical to the one made before).

The real x86 numbers are higher than x64's because the 32-bit build has its own changes, and an address shift inside an enlarged function counts as a change of that function. Every large difference inspected was a real code change.

## IDA

IDA Pro 9.2 handles a PE32 input with no change on exediff's side: headless `idat.exe` analyses it, the database is still `input.exe.i64`, and `hexx64.dll` decompiles 32-bit functions. Checked on `tests\data\x86\old.exe` / `new.exe`: C on both sides of every changed function, a signature for each, none failed.

Signatures were checked by scanning each one in the exe it came from: every signature matches exactly once, at its own function. That is a check of exediff's output, not parity with the Signature Maker plugin on 32-bit; the plugin is not available here, so parity is not claimed.

The `update-signatures` script under `scripts\` works on x64 reports only.

### Against IDA's function list

`Trove_x86.old.exe`, IDA 9.2 auto-analysis (headless, a one-off export, not part of the product) against exediff's 63,516 functions:

| | |
|---|---|
| IDA functions (tail chunks included) | 66,770 |
| IDA starts that exediff also has | 61,590 (92%) |
| of those, the same end too | 61,499 (99.85%); 91 differ (76 where IDA's end is later) |
| IDA functions over 16 bytes (not chunks) | 55,207: 51,999 have the same start, 51,910 the same start and end |
| IDA starts (over 16 bytes) exediff lacks | 3,208: 9 lie inside one of exediff's functions, 3,199 outside every function |
| exediff starts (over 16 bytes) IDA lacks | 1,434 |

The 3,199 are the code the coverage note counts as outside any function: IDA reaches it by its own heuristics (cross references from data, code-pattern scans), exediff's seeds do not. The starts exediff has and IDA lacks are mostly the same code seen from two bytes later (a `call` into the middle of a two-byte `mov edi, edi` prologue that IDA starts at its first byte). No start was skipped. A comparison never sees a function exediff does not have, so the 3.6% outside is the main gap.

IDA decompiled the changed functions of the real pair (old 1,137 requested, new 1,077) with 1 failure per side and about 70 functions per side without a signature; both are reported per function in the report.

## Known limits

- Packed or protected files: the code you can see is the unpacker.
- Data inside code that no seed reaches is outside every function (see the coverage note), and a function reached only through a computed jump is missed.
- A function that ends with a forward `jmp` (a tail jump) and has no `int3` padding after it absorbs everything up to the jump target, unless the function at the target is already known when it is analysed. Which of the two happens can depend on the order functions are found in, so an unrelated change to a caller can move a boundary. Not seen as a problem on the Trove pair (99.85% same end as IDA).
- Padding made of `nop` instead of `int3` (some older toolchains) does not end a function after a `jmp`: `nop` is also used for alignment inside functions.
- The relocation-less fallback masks by range (above).
- Mixed architectures are refused.
